# Related work checked against primary sources

This table records a bounded comparison of the systems named in issue #2737
and the adjacent systems needed to resolve the cited draft passages below.
Every linked page, paper, or project source was opened on 2026-10-21. The
comparison is not an exhaustive literature review and supports no claim that
revl is the first system to address any of these problems.
The classic Sagas paper cited by some drafts was not added as a row because its
primary ACM page and author-hosted copy could not be opened; those draft
citations remain unchecked.

| System | Primary source checked | What it does | How revl differs |
|---|---|---|---|
| Cordis | [Paper, arXiv v1](https://arxiv.org/abs/2608.25512v1), checked 2026-10-21 | Defines a calculus for dynamic plugin composition with revertible effects, reactive coeffects, and metatheorems under explicit component and registry assumptions. | revl checks selected effect and capability declarations and derives component lifecycle order; it does not prove that an external inverse is semantically correct or that host code is sandboxed. See the [reading note](cordis-paper-reading.md). |
| Temporal | [Workflow documentation](https://docs.temporal.io/workflows) and [TypeScript sandbox guide](https://learn.temporal.io/tutorials/typescript/background-check/project-setup/), checked 2026-10-21 | Runs durable workflows as code and replays recorded event histories after failures; the TypeScript SDK bundles Workflow code into a deterministic sandbox and routes nondeterministic I/O through Activities. | revl checks declared effects and derives component teardown; it does not provide a durable workflow service or event-history replay. |
| Restate | [Service and workflow documentation](https://docs.restate.dev/foundations/services), checked 2026-10-21 | Provides durable services, stateful virtual objects, and multi-step workflows with persistent state and interaction handlers. | revl checks effect declarations and lifecycle composition before execution; it does not persist or resume workflow executions. |
| Inngest | [Durable execution primitives](https://www.inngest.com/docs/durable-execution/primitives), checked 2026-10-21 | Saves completed step results and coordinates retries, waits, events, and durable function runs. | revl constrains declared side effects and derives teardown order; it does not checkpoint or resume a workflow run. |
| Microsoft Agent Governance Toolkit | [Governance and ownership policy](https://github.com/microsoft/agent-governance-toolkit/blob/main/docs/GOVERNANCE.md), checked 2026-10-21 | The toolkit describes runtime policy enforcement, identity, sandboxing, and reliability features for autonomous agents. | revl derives effect classes and checks capability reach in a language program; it is not a runtime policy engine or a host-code sandbox. |
| Mastra | [Workflow control flow](https://mastra.ai/docs/workflows/control-flow), checked 2026-10-21 | Builds schema-connected agent workflows from sequential, parallel, conditional, and looping steps. | revl checks effect and lifecycle properties of components; it is not an agent workflow authoring or execution framework. |
| BAML | [Language documentation](https://docs.boundaryml.com/home), checked 2026-10-21 | Provides a DSL for prompting LLMs to produce structured, typed outputs across models and application languages. | revl checks side effects, capability reach, and component lifecycle; it does not define an LLM output schema or structured-generation DSL. |
| Embabel | [Project README](https://github.com/embabel/embabel-agent), checked 2026-10-21 | Provides a JVM framework for defining and running goal-directed agents that use tools and reusable flows. | revl checks declared effects and derives teardown for program components; it does not select or plan agent goals. |
| TypeSpec | [Language overview](https://typespec.io/docs/language-basics/overview/) and [OpenAPI emitter](https://typespec.io/docs/emitters/openapi3/openapi/), checked 2026-10-21 | Describes API models and operations in a language that can emit OpenAPI specifications. | revl checks runtime effect and lifecycle declarations; it does not describe or generate API contracts. |
| RunbookFX | [Demo repository and paper citation](https://github.com/qqyjx/RunbookFX), checked 2026-10-21 | Synthesizes incident-response programs in a typed effect DSL, then checks candidates and replays contracts before execution; the repository labels its demo as synthetic and non-reproducing. | revl checks a general component language's effect and lifecycle rules; it does not synthesize incident diagnoses or runbook programs. |
| TACIT | [Project README](https://github.com/lampepfl/tacit), checked 2026-10-21 | Tracks agent capabilities in types and exposes a sandboxed Scala execution service through MCP. | revl classifies effects and checks component capability reach and teardown; it does not provide a Scala REPL or MCP execution service. |
| ToolGuardian | [Paper, arXiv](https://arxiv.org/abs/2607.21835), checked 2026-10-21 | Uses progressive tool characterization and ASP policies for pre-admission vetting and task-aware runtime authorization. | revl checks effects and capability declarations in source programs; it does not characterize opaque tools or make task-context runtime authorization decisions. |
| Declarative agent workflow paper (arXiv:2512.19769) | [Paper, arXiv](https://arxiv.org/abs/2512.19769), checked 2026-10-21 | Proposes a declarative LLM-agent workflow language that separates pipeline specifications from implementations across language backends and deployment environments. | revl checks declared effects and component lifecycle; it does not provide a cross-language LLM workflow DSL or workflow deployment layer. |
| Open Agent Protocol (OAP) | [Specification repository](https://github.com/openagentprotocol-OAP/oap-spec), checked 2026-10-21 | The repository presents OAP 1.0 as a public working draft for agent discovery, invocation, identity, policy, commerce, and audit interoperability. | revl checks source-level effects and component lifecycle; OAP defines a protocol and interoperability surface rather than a source-language effect checker. |
| typesec-core | [Crate documentation](https://docs.rs/crate/typesec-core/latest) and [source repository](https://github.com/querygraph/typesec), checked 2026-10-21 | Encodes agent permissions, capabilities, secure values, and typestate in Rust traits and types. | revl uses its own source declarations and effect analysis across several backends; it is not a Rust trait library and does not make runtime policy decisions. |
| BoxAgnts | [Project README](https://github.com/guyoung/boxagnts), checked 2026-10-21 | Provides a Rust agent toolbox whose custom tools and skills run in a permissioned WebAssembly sandbox. | revl checks effects and lifecycle at the language boundary; it does not supply an agent product or isolate arbitrary tool binaries in WebAssembly. |
| Koka | [Language book](https://koka-lang.github.io/koka/doc/book.html) and [Perceus paper](https://xnning.github.io/papers/perceus.pdf), checked 2026-10-21 | Infers effect-row types and supports effect handlers; the Perceus paper develops precise reference counting and reuse as implemented in Koka. | revl uses effect classes for reversibility and capability scope, not general control-flow handling; teardown is derived from component dependencies. |
| Eff | [Project overview](https://www.eff-lang.org/) and [effects-and-handlers paper](https://arxiv.org/abs/1203.1539), checked 2026-10-21 | Is a research language for algebraic effects and handlers; its paper gives a denotational semantics and describes a prototype implementation. | revl does not interpret or resume algebraic operations; it checks inverse-or-emission declarations and derives component teardown. |
| Frank | [Paper, arXiv](https://arxiv.org/abs/1611.09259), checked 2026-10-21 | Presents a strict functional language with a bidirectional type-and-effect system and effect handlers. | revl's effect classification is aimed at declared reversibility, capability boundaries, and component lifecycle rather than handler-directed control flow. |
| Scribble protocol language | [Scribble language guide](https://github.com/scribble/scribble-language-guide), checked 2026-10-21 | Describes communication protocols using session types, assertions, and protocol documents, with validation and projection to participants. | revl checks program effects and component lifecycle; it does not specify or project message protocols. |
| seL4 | [Kernel documentation](https://docs.sel4.systems/projects/sel4/index.html), checked 2026-10-21 | Provides a microkernel with machine-checked properties for specified kernel configurations. | revl checks application source declarations and compiler rules; its current implementation is not a verified kernel or a proof of generated runtime code. |
| Instructor | [Project documentation](https://python.useinstructor.com/), checked 2026-10-21 | Uses typed schemas to extract structured data from LLMs, with validation, streaming, and retries. | revl checks program side effects and component lifecycle; it does not validate model output schemas. |
| Pydantic AI | [Output documentation](https://pydantic.dev/docs/ai/core-concepts/output/) and [retry documentation](https://pydantic.dev/docs/ai/core-concepts/retries/), checked 2026-10-21 | Validates structured model outputs and can return validation feedback to the model within a configured retry budget. | revl checks effect and capability declarations; it does not validate or retry generated model outputs. |
| CompCert | [Verified compiler development](https://compcert.org/doc/), checked 2026-10-21 | Gives a machine-checked correctness proof for compilation from CompCert C to supported machine targets. | revl has formal models for selected rules and a checked implementation corpus, but does not prove its shipped compiler/runtime correct by refinement or extraction. |
| CakeML | [Project overview](https://cakeml.org/), checked 2026-10-21 | Develops a HOL-specified ML language and a verified compiler, including a proved-correct backend. | revl's current theorem models do not establish correctness of the shipped Python compiler or its emitted code. |
| eBPF verifier | [Linux kernel verifier documentation](https://docs.kernel.org/bpf/verifier.html), checked 2026-10-21 | Validates eBPF control flow and tracks register and stack states before programs execute in the kernel. | revl checks declared effects and capabilities in its source language; it does not validate kernel bytecode or prove memory safety of arbitrary binaries. |
| Cedar | [Authorization-language paper, arXiv](https://arxiv.org/abs/2403.04651), checked 2026-10-21 | Defines an analyzable authorization policy language for deciding access using principal, action, resource, and context. | revl derives capability reach from program declarations and checks it statically; it is not a general-purpose policy decision point. |
| WebAssembly | [Official specification](https://webassembly.github.io/spec/core/), checked 2026-10-21 | Specifies a portable bytecode, its validation procedure, and execution semantics. | revl's checks concern source-level effects and lifecycle; they do not replace WebAssembly validation or sandbox isolation. |
