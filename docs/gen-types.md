# `revl gen-types`: a model document becomes revl types

**Status:** implemented (`src/revl/gen_types.py`, `tests/test_gen_types_1896.py`),
issue #1896, slice 2. The checked-parser idiom for admitting a data document
(slice 1) waits for `try` (#1900).

```
revl gen-types <model.json> [-o types.rvl] [--json-diagnostics]
```

A product that keeps its data model as data (the entities a user confirmed,
their fields, relations, identity keys, labels and locale) needs revl code
typed against that model, and needs the types to follow the model rather than
drift from it. `revl gen-types` reads one model document and prints revl
source:

- for each entity, a key type for its identity key and a record type;
- one service signature over all of them.

The same document always gives the same bytes. The header carries the sha256
of the model document, and the compiler checks it every time it loads the
file.

It is patterned on `revl import openapi` ([import-openapi.md](import-openapi.md)):
one input document, one generated file with a header saying where it came
from, and a refusal that names the place in the document that is wrong.

## The model document

JSON, version 1. Every key is checked, and an unknown one is refused by name,
so a misspelt `optinal` is an error rather than a required field.

```json
{
  "revl_model": 1,
  "name": "Rentals",
  "locale": "fr-FR",
  "service": "RentalsData",
  "entities": [
    {
      "name": "Customer",
      "label": "Client",
      "key": ["id"],
      "fields": [
        {"name": "id", "type": "Str", "label": "Numéro client"},
        {"name": "email", "type": "Str", "optional": true},
        {"name": "tags", "type": "Str", "list": true}
      ],
      "relations": [
        {"name": "orders", "to": "Order", "many": true}
      ]
    }
  ]
}
```

| Key | Where | Meaning |
|---|---|---|
| `revl_model` | document | the format version; must be `1` |
| `name` | document | the model's name, capitalised (`Rentals`) |
| `locale` | document, optional | the language tag the labels are written in (`fr-FR`) |
| `service` | document, optional | the generated service's name; default `<name>Data` |
| `entities` | document | a non-empty list of entities, in the order the file lists them |
| `name` | entity | the record type's name, capitalised (`Customer`) |
| `label` | entity, field, relation; optional | a display label in the model's locale, carried as a comment |
| `key` | entity | the identity key: a non-empty list of field names, none optional or a list |
| `fields` | entity | a non-empty list of fields |
| `relations` | entity, optional | a list of relations to other entities of the model |
| `name` | field, relation | a lower-case name, not a revl keyword, unique within its entity |
| `type` | field | one of `Str`, `Int`, `Float`, `Bool`, `Bytes` |
| `optional` | field, relation; optional | the value may be absent: `Opt[T]` |
| `list` | field, optional | the value is a list: `List[T]` |
| `to` | relation | the entity it points to |
| `many` | relation, optional | the relation holds several: `List[<To>Key]` |

A relation holds the key of the entity it points to, not the entity itself, so
the record types stay plain data: `customer: CustomerKey` and
`orders: List[OrderKey]`.

### What is refused

Each refusal names the entity and field and gives a JSON pointer and a line:

- an unknown key;
- a field type outside the list above, for example
  `entity \`Order\`, field \`total\`: type 'Decimal' is not a model field type (at #/entities/1/fields/1/type)`;
- a name that is not an identifier of the right case, or is a revl keyword or
  a builtin type;
- a field or relation declared twice in an entity;
- a key that names a missing, optional or list field;
- a relation to an entity the model does not have;
- two entities whose generated names collide (`Order` generates `OrderKey`);
- a `revl_model` other than `1`.

## The generated file

Generated with `-o types.rvl` beside the model, the fixture gives (abridged):

```text
// Generated by `revl gen-types`: do not edit by hand.
// Model document: rentals.model.json
// Model sha256: e214d5640d538e626197fc954c9876bd72bf55ae970f220312f96336b9048b0d
// Model: Rentals (locale fr-FR)
// ...

// Customer: Client
// key: id
//   id: Numéro client
pub type CustomerKey = {
  id: Str,
}

pub type Customer = {
  id: Str,
  name: Str,
  email: Opt[Str],
  tags: List[Str],
  orders: List[OrderKey],
}

service RentalsData {
  // Customer
  fn get_customer(key: CustomerKey) -> Opt[Customer]
  fn list_customer() -> List[Customer]
  emission fn put_customer(record: Customer)
  emission fn delete_customer(key: CustomerKey)
}
```

- **Order.** Entities, fields and relations come out in the order the model
  lists them, so the file reads in the order the model was written.
- **Types.** They are `pub`, so a module `use`s them:
  `use "types.rvl" { Customer }`.
- **The service.** It reads with plain `fn`s and writes with `emission fn`s,
  since a write crosses the system boundary.
- **Labels.** They become comments, with any line break folded to a space,
  so a label cannot end a comment and inject source.

The full output for the fixture is `tests/fixtures/gen_types/rentals.types.golden`.

## The digest check

The header's `Model document:` path is relative to the generated file's
directory, and `Model sha256:` is the sha256 of that document's bytes.

**When the compiler checks it.** Every compile that loads the file checks the
digest against the document: `revl compile`, `revl_check`, admission, and a
module that `use`s it.

**What it refuses**, with category `admission`:
- a model document that has changed since generation: the file is stale, and
  the refusal says to regenerate it;
- a model document that cannot be read;
- a path that leaves the generated file's own directory;
- a header with the first line and not the other two.

**How the model is read.** As an `asset` is:
- a module compiled from disk reads the model from disk, inside the generated
  file's own directory tree;
- an in-memory module (`compile_source(..., modules=...)`, an MCP edit) reads
  it only from the sources map;
- a bare `compile_source` string has no directory to find it in, and is
  refused.

**Where the digest is recorded.** It goes on the IR as `generated_from`, a
list of `{file, model, sha256}` rows present only when a generated file was
compiled. From there it appears in four places:
- the audit (`revl audit`, `revl audit --json`);
- the attested composition hash, which is computed over the IR;
- a component certificate's `subject`, next to the source digest;
- `revl audit`'s text output, as a `generated:` line.

**What is not checked.** The check compares digests. It does not regenerate
the file and compare bytes, so an edit to the body under an intact header is
not caught. Regenerate rather than editing, and keep the generated file and
its model under review together.

`gen-types` itself refuses to write a header whose model path would leave the
output's directory: write the output next to the model, or keep the model in
the output's directory or below it.
