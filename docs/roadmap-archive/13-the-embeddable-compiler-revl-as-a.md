342. ✅ **A single repair/agent loop cannot serve both a sync and an async caller — no sync/async arrow polymorphism (lighthouse-workload finding; the dual of item 92).** Item 92 resolved the async-callback-value problem by having the loop declare its callback async-typed (`complete: (List[Msg]) -> Async[Str]`, resolution (c)), so `author_repair(goal, budget, complete, compile)` in the lighthouse workload's self-evolver is async-parameterized and drives the async `SelfEvolver.author` (where `model.complete` is an `emission async fn`). H19 then needed the SAME repair loop from the agent's tool surface — `ToolRegistry.call`, a NON-async `emission fn` — where the model crossing is genuinely SYNCHRONOUS (a blocking HTTP POST / a scripted read). Two walls: (a) A1 refuses reaching an async op from the sync method, and (b) a sync arrow `(List[Msg]) -> Str` is refused where `(List[Msg]) -> Async[Str]` is expected ("only an arrow may be passed into an async parameter"). So the async-typed loop is UNREACHABLE from the sync caller, and the workload had to duplicate it as `author_repair_sync` (identical control flow, sharing `repair_prompt`/`model_reply_text`; only the arrow color differs). The `Async[Str]` return the design chose for item 92 is now the thing that prevents reuse across the two call sites the same harness naturally has (an async evolve path AND a sync tool-call path over ONE loop). Fix directions: (a) sync/async POLYMORPHISM over a callback parameter — a loop generic in whether `complete` suspends, monomorphized per call site (the caller's color decides), so `author_repair` serves both; or (b) allow a sync `(…) -> T` arrow to satisfy a `(…) -> Async[T]` parameter (a sync value trivially lifts into a completed async), colored at the call site; either removes the duplicate. Repro: one `fn loop(c: (X) -> Async[Y], …)` called once with `x => emit async_op(x)` from an `async fn` and once with `x => emit sync_op(x)` from a sync `emission fn` — the second is refused, forcing a sync twin. `src/revl/lower.py`/`typecheck.py`/`emission_analysis.py` (arrow-color polymorphism / sync-lifts-to-async coercion). LOW-MED (one duplicated loop per shared sync+async workload; the workaround is mechanical).

369. ✅ **WITNESSED INVERSES REPLAY IN REGISTRATION ORDER, NOT LIFO — abort can leave residue or DESTROY pre-session data, and item 244's `stdlib/fs.rvl` reproduces it in three lines (found in revl-harness lane H10; DATA LOSS, contradicts G7 and docs/design/243-witnessed-externs.md §2).** A witnessed effect is auto-approvable *only* because abort provably reverts it — that is the whole argument of 243/246, and it is what item 244's catalog and the harness's H1/H10 lanes sell to an operator. On the py reference tier the promise currently holds only while a session's witnessed ops touch DISJOINT paths: inverses registered from **provide-METHOD invocations** (i.e. every witnessed effect an agent tool fires mid-session, as opposed to one fired from an activation body) replay in REGISTRATION order rather than LIFO, so two ops whose paths overlap undo in the wrong order. Measured on `00ff06c`, py tier, each case a single component and — in the last two — a *single method*, so this is not cross-component teardown ordering, it is the frame's replay order:

    ```
    # via a consumer of stdlib/fs.rvl + stdlib/shell.rvl (revl-harness H10)
    mv a.txt b.txt ; mv b.txt c.txt ; abort  -> leaves b.txt   (should be a.txt)
    rm a.txt       ; touch a.txt   ; abort   -> a.txt is GONE  (pre-session data)

    # via stdlib/fs.rvl alone (revl-harness H1, already landed and shipping):
    write a.txt "V2" ; write a.txt "V3" ; abort
        -> a.txt == "V2"   (should be the pre-session "V1")
    ```

    Read the third one twice: two ordinary writes to one file, then an abort, and the workspace is left holding an intermediate version **that never existed before the session** — neither the pre-session bytes nor the last write. LIFO gives the pre-session bytes; FIFO replays `restore(preimage=V1)` first (correct) and then `restore(preimage=V2)` over the top (wrong). `mv a b ; mv b c` is the cleanest reproducer of all: one method, one op, two invocations — LIFO would `unmove(c->b)` then `unmove(b->a)` and land on `a.txt`; the observed `b.txt` is exactly the FIFO order.     What it contradicts: **G7 (LIFO teardown)** and `docs/design/243-witnessed-externs.md` §2, "Slice 2a as implemented" — *"`Frame.transactional(undo, witness)` returns a `_Transactional` disposer that joins the same LIFO disposer stack as every bracket inverse (so mixed-entry LIFO is preserved for free)"*. Whether the bug is in the accumulator, in the abort drain, or in the contract's silence about the mid-session case is the first thing to determine — the design doc never states which order a post-activation witnessed effect unwinds in, and the answer has to be LIFO for the guarantee to mean anything.

    Why it matters beyond a tidiness bug: 246 auto-approves class (a) crossings **silently, with no prompt**, on the strength of the checked inverse. An out-of-order replay means the runtime silently auto-approved something it cannot revert — the exact failure the classification exists to prevent, and the one an agent harness cannot detect from the outside (abort reports `noResidue: true`; the tree is simply wrong). It is worse than an emission that prompts.

    Cost already paid downstream, as evidence of severity: revl-harness lane H10 could not ship 252's payoff without a **replay-order guard** in its own component — every witnessed arm claims the paths its inverse will touch (both endpoints for `mv`, the target for `rm`/`mkdir`/`cp`/`touch`, ancestor/descendant-aware), and a SECOND witnessed op on a claimed path is routed to the honest `emission` instead.
