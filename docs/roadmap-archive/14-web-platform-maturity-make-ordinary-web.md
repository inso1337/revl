478. ✅ **SECURITY FOLLOW-UP — THE HTTP FACE DROPS `Response.status_text` (2026-09-11, GHSA-q45v-vg29-386j, private).** `stdlib/http.rvl` documents `Response.status_text` as the human-readable reason phrase that travels beside `status`, and every constructor there populates it (`response`, `ok_text`, `ok_json`, `not_found`), but the composed HTTP face read the status and dropped the phrase: `_encode_response_value` built its `HttpReply` from `status`, `headers` and `body` alone, and `_write` called `send_response(reply.status)` with no message. The status line's phrase was therefore whatever `BaseHTTPRequestHandler`'s own table had for the code — the handler's text was unreachable by construction, and a code the table does not know was written with an EMPTY phrase, so the two halves of the documented pair disagreed on the wire. The consumer half of the contract is real and already written down: the exported TypeScript client declares `statusText: string` and fills it from the response object, so it reported a value the server had never sent. Exit: carry the phrase. ✅ FIXED 2026-09-11 (`fix/http-status-text`). `HttpReply` gains a `status_text` field, `_encode_response_value` reads `enc.get("status_text")` and passes it to both of its returns (the `Empty` body branch and the payload branch), and `_write` calls `send_response(reply.status, reply.status_text or None)`. Three details are load-bearing. The `or None` is not cosmetic: `send_response_only` falls back to `self.responses[code][0]` only for `message=None`, while `message=""` writes an empty phrase, so passing `None` when the handler expressed no preference is what keeps every reply that is not a routed `Response` — canonical, manifest, error, refusal — byte-identical to before. The phrase is VALIDATED rather than trusted, because it is written into the status line and a CR or LF in it ends that line early and lets the rest of the value write further fields, a body, or a whole second reply: `_response_refusal` now returns `_UNSAFE_STATUS_TEXT` (a `_FramingRefusal`, so `_write` substitutes a self-written refusal and closes before `send_response` runs) when the phrase fails `_is_field_value`, which is exactly RFC 9110's reason-phrase grammar (HTAB, SP, VCHAR, obs-text) because the two grammars coincide. And an EMPTY phrase is legal rather than refused: it means the handler expressed no preference, which is the fallback case, not a malformed one. **The client-side half needed no change, and that is a finding rather than an omission:** measured with a raw-socket probe that answers `HTTP/1.1 402 Whatever Phrase`, both `fetch` (`statusText`) and `node:http` (`statusMessage`) report the WIRE phrase rather than the standard table's entry, so `export_client.py`'s `__res.statusText` becomes correct the moment the server carries the text, and this is a one-sided fix. **Regression:** `tests/test_serve_http_reason_phrase.py`, 8 checks over a real loopback socket — the handler's phrase reaching the status line for a code inside and outside the table (402, 599, 200), the HTAB control (a legal phrase character is carried, not refused), the two fallback controls (a reply with no phrase, and one whose phrase is empty, both keeping `HTTP/1.1 <code> <table phrase>`), and the two refusal checks (a CRLF phrase and a bare LF phrase both answered with the refusal, the canary body absent and exactly one `HTTP/1.` line on the wire).

Blast radius: the stamp newly ACTIVATES the taint walk for every routed program, so the whole `tests/` suite is the check — 12482 passed / 970 skipped / 20 xfailed, no routed fixture refused. Non-vacuity is pinned too: an unrouted operation's parameter is not a request value, and a routed value reaching only an ordinary emission is still admitted, so ordinary CRUD pays nothing. ✅ FIXED 2026-09-11 (`fix/http-input-taint`). 480. ✅ **SECURITY FOLLOW-UP — THE TWO SHIPPED HEADER READERS DISAGREED ABOUT WHETHER A HEADER WAS PRESENT (2026-09-11, GHSA-pvpr-qr9v-4fx2, private).** `stdlib/http.rvl` documents `header_value`, and `stdlib/framing.rvl` its duplicate-visible `header_values`/`header_count`, as readers over the SAME `List[Header]`, but they compared names by different rules: `header_value` used raw `==` (case-SENSITIVE) while `header_values` compared through a private `name_eq` that ASCII-lower-folded both sides first. RFC 9110 5.1 makes field names case-insensitive, and `framing.rvl`'s own comment says the comparison must work "whatever case a caller stored them in"; `http.rvl` never got that treatment, so for one and the same header list the two shipped readers gave opposite answers about whether a name was present. Reachable on every routed request, not only on hand-built lists: `http_face.py`'s `_build_request` stores the WIRE's own spelling (`[{"name": k, "value": v} for k, v in headers.items()]`), so a handler asking for `authorization` or `content-type` — the idiomatic lowercase spelling — was told the header was absent, while `header_values` on the same list answered the opposite way for the same two spellings. Measured end-to-end through a real loopback socket against the real face: the delivered request carried `{'name': 'Authorization', 'value': ...}`, `header_value(..., "Authorization")` returned the value, and `header_value(..., "authorization")` and `(..., "AUTHORIZATION")` both returned `None`. The impact is a false negative in a presence decision — an authorization or `Content-Type` check that reads the natural spelling — plus two shipped readers of one list contradicting each other. Exit: one comparison, shared. ✅ FIXED 2026-09-11 (`fix/header-name-case`). `stdlib/http.rvl` gains a private `lower_code` and a `pub fn header_name_eq(a, b) -> Bool` that ASCII-lower-folds both sides, `header_value` compares through it, and `stdlib/framing.rvl` imports it and DELETES its private `lower_code`/`name_eq`. The helper lives in `http.rvl` because `framing.rvl` already imports `Header` from there and that dependency must not be reversed. Copying the comparison into `http.rvl` instead was rejected on purpose: a second copy is a second answer to "is this the same field", which is the defect class at issue. The change is in the READERS, not the face, and the face deliberately keeps the wire's own spelling — order and repetition are visible on this type by design (`Header` is a list), so normalising names while building the `Request` would destroy the observability the type exists for. `stdlib/version.rvl`'s stamp is bumped 7 → 8 (a public symbol was added and `header_value`'s behaviour changed), with `tests/test_stdlib_version.py`'s pin raised to match, and `framing.rvl`'s import boundary is now pinned by `tests/test_framing_stdlib.py` with `assert "fn name_eq(" not in text` and `assert "fn lower_code(" not in text`, so a future re-duplication reddens rather than silently reintroducing the second answer. **Regression:** `tests/test_http_stdlib.py::test_a_header_name_is_matched_case_insensitively` (verified to FAIL on the pre-fix `==` reader) and `tests/test_framing_stdlib.py::test_the_two_shipped_header_readers_agree_about_presence`, which compiles a consumer importing BOTH readers and asserts one answer for every spelling and for absence. Three documentation errors the divergence had produced were corrected with it: the `Header` type doc claimed callers normalise names before storing (the face does not, and should not), `http_face.py`'s `_frame_request` docstring claimed `http.rvl` "carries both" reader families (it carries one), and `docs/design/867-request-framing.md` attributed `header_values`/`header_count` to `http.rvl` by omission. Owner: TBD.

481. ✅ **SECURITY FOLLOW-UP — THE SHELL CLASSIFIER AUTO-APPROVED A LINE CONTINUATION AND PLANNED A PATH THE COMMAND NEVER TOUCHED (2026-09-11, GHSA-h52r-mm26-7vmc, private).** `stdlib/shell.rvl`'s `classify` is the gate that decides whether a command may be auto-approved as reversible `witnessed` or must take one honest `emission` prompt, and for `mv`/`rm`/`cp`/`mkdir`/`touch` it lowers the command text into a plan plus the inverse that undoes it — that plan IS the justification for "reversible, so it needed no approval", and it is the audit record of what happened. `_first_unquoted_metachar` RECOGNISED a backslash-newline and then skipped it, on the comment's own reading of it as "a line-continuation backslash-newline, or an escaped char: the next character is literal data". A backslash-newline is not an escaped newline: it is a shell line continuation, so `/bin/sh` DELETES the pair and JOINS the words around it, while `shlex.split` (and the ts port's `shlexSplit`) keep a LITERAL newline in the token. Measured against the real `/bin/sh` through an argv-recording shim on `PATH`: `mv a\<nl>b dest` was classified `witnessed` with `args=['a\nb', 'dest']`, the shell ran `['ab', 'dest']`, and the recorded inverse `unmove('a\nb', 'dest')` named a path that never existed, so the mutation was recorded as reversible and was not — the preimage stayed where the shell had put it under a name the plan never mentioned. The join also crosses QUOTE BOUNDARIES, which no tokenizer can express at all: `mv 'x'\<nl>'y' dest2` planned `args=['x\ny', 'dest2']` while the shell ran `mv xy dest2`, one word `xy` joined across two single-quoted strings — so this was never a tokenizer bug that more careful `shlex` use would have caught, it is a word-formation rule outside the model the tokenizer implements. The module already refused a bare newline (`if c == "\n" or c == "\r": return "\n"`); the continuation was the one spelling of "this command spans lines" that slipped past that same refusal, in the double-quote branch too, where the generic `i += 2` consumed the pair with no `\n` check. Exit: refuse the continuation. Both branches of `_first_unquoted_metachar` and of the ts `firstUnquotedMetachar` now return `"\n"` for a backslash-newline, routing to `_emission(cmd, "command spans multiple lines")`. Teaching the tokenizer the shell's join rule was considered and rejected on purpose: it would have to reproduce a rule that crosses quote boundaries, and the module's stated contract is that every ambiguity resolves toward `emission`, because a false `emission` costs one prompt while a false `witnessed` auto-approves an effect the system cannot undo. Non-vacuity is pinned in both directions: a continuation INSIDE single quotes is literal data and still lowers (`mv 'a\<nl>b' dest3` keeps the three-character operand on both sides), so the change is a refusal of the continuation and not of backslashes or newlines generally. Differential evidence: a harness compared the classifier's plan against the argv the real `/bin/sh` produces, first over a hand-built edge-case set (vtab, formfeed, tab, CR, hash, empty operands, unterminated quotes, trailing backslash, escaped space, nbsp, emspace, nested quotes, dollar-brace, backtick) and then over a cross-product fuzz of 2800 commands (40 word atoms x 6 command spellings x 2 arities) — pre-fix 211 divergences out of 836 auto-approved commands, every one this class, post-fix 0 divergences and `DIVERGENCES: []` on the hand-built set. ✅ FIXED 2026-09-11 (`fix/shell-line-continuation`). **Regression:** `tests/test_shell_classify.py`'s new `_LINE_CONTINUATIONS` (8 cases: unquoted, leading, double-quoted, cross-quote, and the `rm`/`cp`/`mkdir`/`touch` forms) with `test_line_continuation_refuses` and the positive control `test_line_continuation_inside_single_quotes_still_lowers`; three continuation cases added to `tests/test_ts_witnessed_parity.py`'s `_EMISSION` and `"mv 'a\<nl>b' c"` to its `_WITNESSED`, so the live py-vs-ts cross-tier diff pins both ports rather than one; and one labelled entry in `tools/shell_witnessed_corpus.py`, driven by `tests/test_shell_witnessed_corpus.py`. Owner: TBD.

483. ✅ **SECURITY FOLLOW-UP — `json_stringify` ENCODED A NON-FINITE `Float` FOUR DIFFERENT WAYS (2026-09-12, GHSA-3j5r-h8r6-wvq6, private).** `stdlib/json.rvl`'s `json_stringify(v: Any) -> Str` is `pure`, so `docs/syntax-2.0.md` §3.4 requires ONE byte string on every tier; a non-finite `Float` produced four. Measured on `f86aa8fb` with the probe `json_stringify(1.0/0.0)`: py returned `Infinity`, ts `null`, rust `null`, and go the EMPTY string. The read side diverged with it — `json_try_parse("NaN")` (and `"Infinity"`/`"-Infinity"`) was `Ok` on py and `Err` on ts/rust/go, because `json.loads` passes those constants through by default while `serde_json` and `encoding/json` are strict and the `@ts` hand-written parser has no `N`/`I` production at all. 511. ✅ **SECURITY FOLLOW-UP — THE TRUC VENDORING WRITE ASKED FOR MODE `0o666`, SO UNDER A PERMISSIVE UMASK IT HANDED EVERY LOCAL ACCOUNT WRITE ACCESS TO A FILE THE COMPILER LATER READS AND EXECUTES (2026-09-18, CodeQL `py/overly-permissive-file`, alert 58).** `src/revl/truc/_host.py`'s `_write_no_follow` is the single write path for a vendored entry — `truc add`/`truc ship` and the name-jail tests all funnel through it — and it opened the destination with `os.open(path, os.O_WRONLY | os.O_CREAT | os.O_TRUNC | _O_NOFOLLOW, 0o666)`. `0o666` is the mode a bare `open(path, "w")` asks for, and it is only ever a REQUEST: the kernel masks it with the umask, so on the common `022`/`002` umasks the entry lands `0o644`/`0o664` and nothing is wrong. But the request is granted literally under a permissive umask — `000`, which is common in containers and some CI images — and the file it creates is vendored project SOURCE that the compiler later reads and executes, so the wrong umask turns every local account into a writer of the build inputs. The fix is to state the intent the code already had: `0o644`, world-readable and never group- or world-writable, safe under any umask. It is a hardening change rather than a repair of an observed compromise: nothing in the tree claimed the file was `0o644`, and the escalation needs an attacker already local to the machine. No test asserted the mode — `grep -rn "0o6\|st_mode\|S_IMODE\|chmod"` over `tests/` and `src/revl/truc/` finds no assertion on the created entry's permissions — so the regression is the absence of an assertion rather than a flipped one, and the tests confirm the change is behaviour-preserving for everything the write path actually promises: `pytest tests/test_truc_name_jail.py tests/test_truc_path_jail.py tests/test_truc_bootstrap.py tests/test_truc_ship.py tests/test_truc_add_assemble.py` → 125 passed, 29 skipped. Residual: the fix narrows the REQUESTED mode only; the file's final mode is still whatever the umask allows, so a caller that needs a stronger guarantee must `fchmod` the open descriptor, which this path deliberately does not do because the vendored tree is public source.
