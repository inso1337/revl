# Seeded-defect saga corpus (issue #2736)

A measured corpus of small sagas with known saga defects. It answers
one question for the revl side of the paper's evaluation: for each seeded
defect, is it refused at compile time, caught only by a fault test, or missed
by both?

This is the **first slice** of [issue #2736](https://github.com/inso1337/revl/issues/2736).
The hand-written Temporal TypeScript port and sagas written by people who did
not build the checker are the second slice; they are not scored here, and the
results file says so rather than guessing their column.

## Layout

- `defects.json`: the corpus. One row per defect: id, group, defect kind,
  saga file, the defect as a sentence, and the expected catch point. The list
  was written before the sagas; each saga is one row's defect and nothing
  else.
- `sagas/`: one self-contained `.rvl` composition per row. Most rows are the
  same small checkout saga (an inventory hold, a payment authorization, and a
  settlement emission, each with its inverse or compensation); the
  `dependency-cycle` row is a two-component composition. The seeded defect is
  the only difference from a clean saga.
- `run.py`: the verdict runner. It compiles each row, runs
  `revl test --sweep` on the rows that compile, prints the table, and writes
  `bench/results/saga-defect-corpus.md`.
- `../results/saga-defect-corpus.md`: the measured table. Generated by
  `run.py --write`; never edited by hand.

## The three verdicts

| verdict | meaning |
|---|---|
| `compile` | the checker refused the saga, so the defect cannot reach a run |
| `fault-test` | the saga compiled and the fault sweep failed at a seeded fault |
| `missed` | the saga compiled and every sweep unit passed |

`missed` is a result, not a failure of the runner. The corpus exists to record
what the checker and the sweep do not catch as much as what they do.

## Run it

The fault sweep executes the py reference tier, so it needs the cordis-py
runtime at the pin in `backends/python/setup.sh`:

```sh
sh backends/python/setup.sh          # or a lane venv with the pinned cordis-py
python3 bench/saga_defects/run.py     # measure and print
python3 bench/saga_defects/run.py --write   # measure and refresh the table
python3 bench/saga_defects/run.py --list    # rows only, no measurement
python3 bench/saga_defects/run.py --only wrong-release-sku
```

Without cordis-py the command exits 2 and says why. It never reports the
runtime rows as a pass it did not measure.

The command exits 1 when a row has no verdict, when a measured verdict
disagrees with `expected`, or when `expectedCode` disagrees with the refusal
code. That is deliberate: the expected catch point is the corpus's ground
truth, so a checker improvement that starts catching a `missed` row fails the
command until the row is updated. Do not update it without re-reading the
saga and stating in the row what now catches it.

## What the corpus does not measure

- **Not third-party code.** Every row in this slice is in the `project` group,
  written by the people who built the checker. `defects.json` reserves the
  `outside` group for sagas the checker's authors did not write; it is empty
  until the second slice. Same-author bias is not removed.
- **Not real bugs.** The defects are seeded. The table measures which
  mechanism catches a known seeded defect, not how often real sagas contain
  one, and it says nothing about author burden or false-positive rate.
- **No Temporal column.** The hand port and its score are the second slice.
  The corpus is written so the same rows can be ported without rewriting the
  defect list: the row is the defect, the saga is one rendering of it.
- **A narrow failure model.** The sweep is sequential, single-fault and
  top-level (`docs/fault-tests.md` sections 9.3 and 9.5). A `missed` row is
  missed by *this* sweep, not necessarily by every test a careful author
  could write.
- **Provider state is visible only where the provider is a revl `Map`.** In
  most sagas the inventory and payment stores are `Map`-backed, so a wrong
  undo that leaves a key behind is residue the sweep can read.
  `wrong-refund-order` uses an opaque host-body provider and the same kind of
  wrong target is missed. A caught row is therefore optimistic for an
  external service; the pair of rows is there to show the boundary rather
  than hide it.
- **G3 here is component dependency acyclicity**, not a check on the order of
  steps inside a saga. The `dependency-cycle` row is a composition-level
  defect; the ordering rows are scored on their own.

## Adding a row

1. Write the defect as a sentence in `defects.json` first: id, group, kind,
   saga, file, `expected`, and `expectedCode` when the expected verdict is
   `compile`. Runtime rows also name the `component` the sweep targets.
2. Add the saga under `sagas/`, with the defect visible in a comment at the
   top. One defect per file.
3. Run the command. If the measured verdict disagrees with the row, fix the
   saga or the row; do not loosen the check.
4. Run with `--write` and commit the refreshed results table.

The files are compiled by the real checker and executed by the real fault
sweep. There is no bespoke model of either.
