# Seeded-defect saga corpus (issue #2736)

A measured corpus of small sagas with known saga defects. It answers
one question for the revl side of the paper's evaluation: for each seeded
defect, is it refused at compile time, caught only by a fault test, or missed
by both?

This is [issue #2736](https://github.com/inso1337/revl/issues/2736). The revl
side is `run.py`; the Temporal TypeScript side, the same rows ported and scored
on a real Temporal server, is `run_temporal.py` (see
[The Temporal side](#the-temporal-side)). Sagas written by people who did not
build the checker are not in the corpus yet.

## Layout

- `defects.json`: the corpus. One row per defect: id, group, defect kind,
  saga file, the defect as a sentence, and the expected catch point. The list
  was written before the sagas; each saga is one row's defect and nothing
  else.
- `sagas/`: one self-contained `.rvl` composition per row. Most rows are the
  same small checkout saga (an inventory hold, a payment authorization, and a
  settlement emission, each with its inverse or compensation); the
  `dependency-cycle` row is a two-component composition. The seeded defect is
  the only difference from a clean saga.
- `run.py`: the verdict runner. It compiles each row, runs
  `revl test --sweep` on the rows that compile, prints the table, and writes
  `bench/results/saga-defect-corpus.md`.
- `../results/saga-defect-corpus.md`: the measured table. Generated by
  `run.py --write`; never edited by hand.
- `temporal/`, `run_temporal.py`, `../results/saga-defect-corpus-temporal.md`:
  the Temporal side, below.

## The three verdicts

| verdict | meaning |
|---|---|
| `compile` | the compiler refused the saga, so the defect cannot reach a run |
| `fault-test` | the saga compiled and the fault sweep failed at a seeded fault |
| `missed` | the saga compiled, the sweep ran at least one step, and every sweep unit passed |

A `compile` verdict is reported as one of two refusals, and the totals count
them apart:

- a **checker refusal**: a named rule refused the saga (G3, G4, G5 and so on).
  Some rules run in the parser (the G4 missing-undo refusal does); they are
  still checker refusals, because the message names the rule.
- a **parse refusal**: the parser's generic syntax error (`expected ...,
  found ...`), the shape `revl.diagnostics.classify` maps to `SYNTAX`. It
  names no rule and any typo would earn it, so it is not evidence that a
  reversibility check fired. `emission-with-undo` is the one such row; it
  records `"refusal": "parse"`, and the runner fails if the measured kind
  disagrees with the row.

`missed` is a result, not a failure of the runner. The corpus exists to record
what the checker and the sweep do not catch as much as what they do. A sweep
that ran zero steps, a crash of the sweep driver, and a row that does not
finish within `--timeout` are runner errors (exit 1), never `missed` or
`fault-test`.

### Rows that are one defect kind

Two rows can carry the same defect kind at different sites. `missing-undo-hold`
and `missing-undo-auth` are one defect kind (an `effect` with no `undo`) at the
two call sites of the same checkout saga. They are kept as two rows, so the
checker-refusal count is a count of rows, not of distinct defects; the results
file reports the distinct defect kinds next to each count and names the rows
that share one.

## Run it

The fault sweep executes the py reference tier, so it needs the cordis-py
runtime at the pin in `backends/python/setup.sh`:

```sh
sh backends/python/setup.sh          # or a virtual environment with the pinned cordis-py
python3 bench/saga_defects/run.py     # measure and print
python3 bench/saga_defects/run.py --write   # measure, and refresh the table if no row drifted
python3 bench/saga_defects/run.py --timeout 60   # stop any row that runs longer (default 300 s)
python3 bench/saga_defects/run.py --list    # rows only, no measurement
python3 bench/saga_defects/run.py --only wrong-release-sku
```

Without cordis-py the command exits 2 and says why. It never reports the
runtime rows as a pass it did not measure.

The command exits 1 when a row has no verdict, when a measured verdict
disagrees with `expected`, when `expectedCode` disagrees with the refusal
code, or when `refusal` disagrees with the measured refusal kind. With
`--write`, a drifting run leaves the results file as it was. That is
deliberate: the expected catch point is the corpus's ground truth, so a checker improvement that starts catching a `missed` row fails the
command until the row is updated. Do not update it without re-reading the
saga and stating in the row what now catches it.

## What the corpus does not measure

- **Not third-party code.** Every row is in the `project` group, written by
  the people who built the checker. `defects.json` reserves the `outside` group
  for sagas the checker's authors did not write; it is empty until the owner
  supplies some. Same-author bias is not removed.
- **Not real bugs.** The defects are seeded. The table measures which
  mechanism catches a known seeded defect, not how often real sagas contain
  one, and it says nothing about author burden or false-positive rate.
- **No Temporal column in this table.** The Temporal ports are scored by
  `run_temporal.py` into their own results file, next to this one.
- **A narrow failure model.** The sweep is sequential, single-fault and
  top-level (`docs/fault-tests.md` sections 9.3 and 9.5). A `missed` row is
  missed by *this* sweep, not necessarily by every test a careful author
  could write.
- **Provider state is visible only where the provider is a revl `Map`.** In
  most sagas the inventory and payment stores are `Map`-backed, so a wrong
  undo that leaves a key behind is residue the sweep can read.
  `wrong-refund-order` uses an opaque host-body provider and the same kind of
  wrong target is missed. `partial-refund` is caught only because its ledger
  keeps the charged amount in the `Map` and a refund subtracts from it, so
  half a refund leaves the other half behind; with a full refund the same
  saga passes every sweep unit. A provider that only records that an order
  was charged could not express a partial refund at all. A caught row is
  therefore optimistic for an external service; the pairs of rows are there
  to show the boundary rather than hide it.
- **G3 here is component dependency acyclicity**, not a check on the order of
  steps inside a saga. The `dependency-cycle` row is a composition-level
  defect. A wrong LIFO order cannot be written in revl source: teardown order
  is derived from source order, and the only author control is the target of
  each inverse. The nearest expressible defect is a swapped inverse target
  (`wrong-release-sku`, `wrong-refund-order`), which is why both carry the
  `wrong-inverse-target` kind. A hand-written teardown that would impose an
  order itself is refused at G5 (`manual-teardown`).

## Adding a row

1. Write the defect as a sentence in `defects.json` first: id, group, kind,
   saga, file, `expected`, and `expectedCode` when the expected verdict is
   `compile`. Runtime rows also name the `component` the sweep targets.
2. Add the saga under `sagas/`, with the defect visible in a comment at the
   top. One defect per file.
3. Give the row a `temporal` entry: the edits that seed the same defect in the
   Temporal port, or `no-counterpart` and the reason (see below). A row with no
   entry is a data error, so no row is silently left unscored.
4. Run the command. If the measured verdict disagrees with the row, fix the
   saga or the row; do not loosen the check.
5. Run both runners with `--write` and commit the refreshed results tables.

The files are compiled by the real checker and executed by the real fault
sweep. There is no bespoke model of either.

## The Temporal side

The same defect list scored on a Temporal TypeScript saga, so the comparison
the paper needs has analogous seeded defects on both sides: the row's defect,
written in each system's terms. The defect list is data and each system's
version is derived from it:

- `temporal/src/workflows.ts` holds the **clean** ports: the `checkout` saga the
  corpus seeds, and `examples/migrator.rvl` (a lock, an await, an emission with a
  compensation). They are written the way Temporal's own saga guidance writes
  them: a stack of compensations, each registered before its forward activity,
  drained newest first, continuing past one that raises.
- `temporal/src/activities.ts` and `state.ts` are the operator's side: the
  activities, a fake world they act on, and a journal of what ran.
- Each row's `temporal` key in `defects.json` is the seeded port as data: text
  edits to the clean files, applied by the runner, each of which must match
  exactly as often as it says. `run_temporal.py --emit DIR` writes the derived
  ports for review. A reviewer reads the edit list against the row's
  description; nobody judges a port by one author's reading of a hand-written
  file.
- A row whose defect has no Temporal counterpart says why (`no-counterpart`)
  instead of being scored: the defect is a violation of a rule that Temporal
  does not have, so no Temporal program is the same saga with this defect.
- `wrong-lifo-order` is a Temporal-only row: it can be written in Temporal
  (push instead of unshift) and cannot in revl, where the order is derived.

`run_temporal.py` type-checks every port with `tsc`, then runs it on a real
Temporal dev server once with no fault, to count its failure points, and once
with a failure injected after each step (`faultPoint` calls the port places
after each step, the counterpart of the `fail` step revl's sweep splices in).
It judges what the fake world and the journal show with the three assertions of
revl's py-tier sweep that apply to one workflow: the saga failed; the world is
empty again and no compensation raised; the compensations that ran, ran newest
first. A port that fails with no fault injected, a port with no failure points,
a run that fails with anything but the injected fault, and a server that is
missing or silent are runner errors, never verdicts.

```sh
temporal server start-dev --headless          # or any Temporal dev server
(cd bench/saga_defects/temporal && npm ci)
REVL_TEMPORAL_DEV_SERVER=127.0.0.1:7233 python3 bench/saga_defects/run_temporal.py
REVL_TEMPORAL_DEV_SERVER=127.0.0.1:7233 python3 bench/saga_defects/run_temporal.py --write
python3 bench/saga_defects/run_temporal.py --emit /tmp/ports   # the derived ports, no server
```

What it does not measure, beyond the limits above:

- The ports, the fake world and the assertions were written by the same people
  as the revl corpus, as analogues of revl's sweep. A Temporal team would write
  their own harness; this one is a harness for this corpus.
- The harness holds no list of what a port registered, so it does not check that
  a compensation was owed; `missing-compensate` is missed on both sides for
  different reasons. The order assertion is skipped when a compensation repeats,
  so `double-release` is not judged for order.
- The clean ports use the documented compensation-stack idiom. A typed helper
  that pairs each forward step with its compensation would move the
  `missing-undo` rows into `tsc`. The numbers compare revl with that idiom, not
  with every library a Temporal user could write.
- The fake world is readable by the test, so a wrong inverse is visible. The
  `wrong-refund-order` port makes the payment store opaque, as the revl row
  does, so that row is missed on both sides by construction: it measures what a
  test can see, not the two systems.
- A failure is injected at the boundary after a step. The case where a forward
  activity commits and then reports failure is not injected, on either side.
